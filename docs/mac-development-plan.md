# macOS Desktop 开发总计划

状态：计划中  
范围：`mac/` 原生 macOS SwiftUI 客户端  
依据：[ADR-003](decisions/003-add-macos-desktop.md)、[第一版需求](product/requirements.md)、[数据模型](reference/data-model.md)、[JSON 导入格式](reference/import-format.md)

## 一、总体目标

在不破坏现有 Android 客户端的前提下，新增一个使用 SwiftUI 和 Liquid Glass 的 macOS App，完成卡组浏览、卡片管理、JSON 导入、本地保存和悬浮卡片学习。macOS 首期不提供朗读和跟读识别，学习交互通过置顶窗口和键盘上下键完成。

总体原则：

- `android/` 与 `mac/` 独立构建、独立测试、独立实现平台 API。
- 两端通过数据格式、领域规则和文档保持行为一致，不立即引入 Kotlin Multiplatform。
- 先完成可用的桌面基础闭环，再增加语音能力。
- 所有阶段都必须保证 Android 现有构建和测试不回退。

## 三、阶段子计划

### 阶段 0：范围冻结与环境准备

目标：确认 macOS 首期边界，建立独立 Xcode 工程和验证基线。

子任务：

- 确认最低 macOS 版本、Xcode 版本和 Apple Silicon 支持范围。
- 确认 `mac/` 工程采用 SwiftUI、Observation、SQLite 和 Swift Package Manager。
- 盘点 Android 数据模型、JSON 导入格式和 Learning Engine 行为。
- 建立 macOS 构建、单元测试和本地运行命令。
- 明确 Liquid Glass 不可用时的 Material/不透明降级方案。

完成标准：空白 macOS App 可以启动，窗口和基础测试通过，Android 基线检查结果已记录。

### 阶段 1：工程骨架与 Liquid Glass 壳层

目标：完成桌面 App 的窗口、导航和视觉基础。

子任务：

- 创建 `mac/` SwiftUI App。
- 建立 App、RootView、ViewModel、Models、Data、Features、Platform 目录。
- 实现主窗口、侧边栏或导航栏、工具栏、菜单和快捷键。
- 建立 Liquid Glass 设计令牌：颜色、圆角、间距、材质、强调色和可读性规则。
- 加入浅色/深色模式、动态字体、键盘焦点和无障碍标签。
- 建立不支持 Liquid Glass 时的兼容样式。

完成标准：用户可以启动 App，在首页、我的页面之间导航；窗口缩放、主题切换和键盘操作正常。

### 阶段 2：本地数据层与 JSON 导入

目标：让 macOS 可以可靠保存和导入真实卡组数据。

子任务：

- 根据现有数据模型设计 SQLite schema。
- 实现数据库初始化、版本号和迁移机制。
- 实现 Deck、Card、Progress、Attempt、Settings Repository。
- 实现文件选择器和 UTF-8 JSON 导入。
- 复现字段校验、2 MiB 文件限制、1000 张卡片限制和重复指纹规则。
- 使用事务保证批量导入全成或全败。
- 为数据层、迁移和导入错误增加 Swift 单元测试。

完成标准：导入 Android 现有示例数据后，关闭并重新打开 App，数据和顺序保持一致。

### 阶段 3：卡组、卡片和设置 UI

目标：完成非学习场景的核心桌面体验。

子任务：

- 实现卡组首页、搜索、空状态和导入入口。
- 实现卡组创建、编辑、删除和删除确认。
- 实现卡组详情、卡片列表、卡片排序和卡片数量显示。
- 实现卡片创建、编辑、删除和正文校验。
- 实现“我的”页面：默认学习模式、朗读速度、自动翻页延迟。
- 统一处理加载、保存失败、空数据和重复导入提示。

完成标准：不依赖语音功能即可完成卡组和卡片的完整增删改查。

### 阶段 4：手动学习闭环

目标：先提供稳定、可验收的无语音学习流程。

子任务：

- 实现从卡组详情进入学习页面。
- 实现正面/背面、翻面、左右切卡和循环边界。
- 实现当前位置保存与恢复。
- 实现暂停、退出和窗口关闭时的状态保存。
- 实现窗口失去焦点后的安全暂停策略。
- 为学习状态、切卡和恢复位置增加测试。

完成标准：用户可以离线打开卡组、连续学习、退出后重新进入并恢复到上次位置。

### 阶段 5：macOS TTS

目标：接入原生 macOS 朗读，不影响手动学习主流程。

子任务：

- 定义 macOS `SpeechPlayer` 协议和状态模型。
- 使用 `AVSpeechSynthesizer` 实现播放、暂停、继续、停止和完成回调。
- 处理句子/短语分段、朗读速度和卡片切换取消。
- 为每次朗读生成并校验 `operationId`，忽略迟到回调。
- 将朗读失败、无可用语音和用户取消转换为领域错误。
- 在真实 Mac 上验证普通话语音和窗口生命周期。

完成标准：手动学习支持稳定朗读；切卡、退出和后台/非活动场景不会继续朗读旧卡片。

### 阶段 6：跟读识别与自动学习

目标：在语音原型验证通过后，再实现自动跟读和自动播放。

子任务：

- 先验证 macOS 端 Vosk 或系统语音 API 的可用性、许可证和性能。
- 定义麦克风权限说明、请求和拒绝后的降级路径。
- 实现录音会话、停止收音、部分结果和最终结果处理。
- 复用文档规定的文本匹配行为，但用 Swift 实现并建立对照测试。
- 实现“朗读完成 → 开始跟读 → 判断完成 → 翻面 → 下一张”的状态机。
- 实现自动播放和暂停、重读、切卡时的资源清理。
- 覆盖 `operationId`、窗口失焦、权限撤销和语音中断场景。

完成标准：真实 Mac 上自动跟读连续运行，旧回调不会推进错误卡片；识别不可用时仍可切换手动学习。

### 阶段 7：发布准备

目标：形成可交付的 macOS 构建和验收结果。

子任务：

- 完成 macOS 单元测试、UI 测试和真实设备验收。
- 验证 Apple Silicon 构建；再决定是否发布 Intel 构建。
- 配置 App 图标、Bundle Identifier、版本号和最小系统版本。
- 配置签名、公证和分发包生成。
- 编写 macOS 安装、权限说明、数据位置和故障排查文档。
- 回归 Android 构建、单元测试和已有真机语音验收。

完成标准：生成可安装的签名包，核心功能验收记录完整，Android 无回归。

## 四、第一批具体步骤

第一批只做阶段 0 和阶段 1 的最小闭环：

1. 检查当前 Mac 的 Xcode、Swift 和 macOS 版本。
2. 创建 `mac/` SwiftUI App，确保不修改现有 `android/` 源码。
3. 建立 `mac/README.md`，记录本地构建、运行和测试命令。
4. 建立 macOS 目标目录和基础目录结构：`App`、`Features`、`Data`、`Domain`、`Platform`、`DesignSystem`。
5. 实现带 Liquid Glass/兼容降级样式的主窗口和首页空状态。
6. 实现“首页”和“我的”两个导航入口，以及桌面菜单和快捷键占位。
7. 添加第一个 Swift 单元测试和一个窗口启动验收清单。
8. 执行 macOS 构建与测试，并记录 Android 基线结果。

第一批完成后，再进入数据层；不在工程骨架阶段提前接入 TTS、Vosk 或复杂同步逻辑。

## 五、验收与风险控制

每个阶段完成时都检查：

- Android 工程现有改动不被覆盖，且 Gradle 构建和单元测试可运行。
- macOS UI 不直接访问 SQLite、TTS 或识别器。
- Liquid Glass 不导致正文、焦点和错误提示不可读。
- 文件导入和数据库写入失败时不产生半成品数据。
- 语音回调携带 `operationId`，退出、切卡和失焦后忽略旧回调。
- 真实 Mac 验证语音和权限；不能只用 Swift 单元测试代替。

主要风险：

- Liquid Glass 的 API 与最低 macOS 版本存在兼容差异。
- macOS 端 Vosk 集成、模型分发和麦克风权限需要单独做技术预研。
- Android 与 Swift 两套 Learning Engine 可能出现行为漂移，因此必须以同一组 JSON/状态场景做对照测试。
- 数据迁移和文件路径不能假设 Android 的目录结构，必须使用 macOS 应用容器目录。
